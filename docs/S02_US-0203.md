**Statut :** **IMPLEMENTED — REVIEW WINDOWS/POSTGRES REQUIRED**

## Objectif

Éviter tout mélange juridique entre sociétés en rendant l'entité juridique obligatoire dans les flux métier qui existaient déjà, tout en conservant la compatibilité avec le vertical slice SCI.

## Livrable

### Base de données

Migration : `0008_entity_data_isolation.sql`.

`legal_entity_id` est ajouté et rendu obligatoire sur 19 tables métier. Les données existantes sont backfillées avant passage en `NOT NULL`.

Les relations critiques sont cloisonnées par FK composites :

- unité → bien ;
- bail → unité ;
- bail → locataire ;
- facture → bail ;
- encaissement → facture ;
- tâche → règle ;
- document en inbox → stockage.

Les unicités importantes de règles, tâches, échéances, banque, paramètres, comptes IA/e-mail et inbox incluent désormais l'entité.

### Runtime

`src/entity_scope.rs` fournit `current_legal_entity_id()` et `set_active_legal_entity()`.

`src/server.rs` et `src/intelligence.rs` utilisent cette portée pour les lectures, écritures, mises à jour et suppressions métier.

Le contexte assistant est désormais explicitement `legal_entity_id`.

### UI

`src/ui.rs` ajoute un sélecteur d'entité active dans la barre supérieure. Un changement d'entité revient au tableau de bord et relance le rafraîchissement.

### Stock

Aucune table de stock n'existe dans le schéma historique ; aucune table fictive n'a été créée. Toute extension stock future devra suivre le même périmètre `legal_entity_id`.

## Compatibilité

- `sci_id` est conservé sur les tables historiques qui en disposaient.
- Les tables génériques permettant à une SARL de fonctionner sans seconde SCI rendent `sci_id` nullable.
- Les relations historiques SCI restent cohérentes grâce aux FK composites lorsque `sci_id` est renseigné.
- Les modules patrimoine/locataires/associés historiques restent explicitement SCI-only dans cette story lorsqu'ils nécessitent encore la table `scis`.
