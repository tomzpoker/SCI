**Projet :** SCI Family Rust

**Sprint :** S01 — Socle technique + continuité  
**User Story :** US-0104  
**Dépendance :** US-0101, avec conservation des livrables US-0102 et US-0103  
**Statut livrable :** **IMPLEMENTED — REVIEW WINDOWS REQUIRED**

## User story

En tant qu'exploitant, je veux diagnostiquer les erreurs avec des journaux structurés et un identifiant de suivi exploitable.

## Critères d'acceptation

- Les logs application, sécurité, métier, fiscal, automation, OCR, bank, AI et migration sont structurés avec `error_id` pour les erreurs/avertissements.
- Les tests et la documentation nécessaires sont inclus avant Ship.
- Aucun secret de configuration n'est recopié dans les logs.

## Research

L'existant possédait déjà `tracing` et `tracing-subscriber`, mais l'initialisation était directement codée dans `main.rs` et les erreurs n'avaient pas d'identifiant corrélable.

Le pipeline documentaire contenait des warnings non structurés et le runner SQLx de migration produisait principalement des sorties texte.

## Design

La couche d'observabilité est centralisée dans :

`D:\SCI\DEV\SCI-family-rust\src\observability.rs`

Les domaines normatifs sont :

- `application`
- `security`
- `business`
- `fiscal`
- `automation`
- `ocr`
- `bank`
- `ai`
- `migration`

Chaque erreur ou avertissement reçoit un identifiant `ERR-<UUID>`.

En mode serveur, `tracing-subscriber` produit des événements JSON. Le niveau de filtrage reste contrôlable par `RUST_LOG`.

Aucune URL de base de données, aucun mot de passe, aucune pièce jointe, aucun contenu de mail et aucun secret n'est journalisé par cette story.

## Review

### Gate statique

```powershell
cd D:\SCI\DEV\SCI-family-rust;powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify-observability.ps1
```

### Tests Rust

```powershell
cd D:\SCI\DEV\SCI-family-rust;cargo test --lib --features server
```

### Build serveur

```powershell
cd D:\SCI\DEV\SCI-family-rust;cargo check --features server
```

### Vérification opérationnelle

Lancement serveur avec JSON :

```powershell
cd D:\SCI\DEV\SCI-family-rust;$env:RUST_LOG='info';cargo run --features server
```

Le démarrage doit produire un événement `event=server_started` avec `domain=application`.

Un échec du cycle automation doit produire un `error_id` avec `domain=automation`.

Le runner migration doit produire `domain=migration` et un `error_id` en cas d'échec.

## Ship gate

US-0104 ne doit pas être marqué `SHIPPED` avant :

1. `verify-observability.ps1` vert ;
2. `cargo test --lib --features server` vert sur Windows/MSVC ;
3. `cargo check --features server` vert ;
4. vérification visuelle d'au moins un événement JSON `application` et un événement `automation` ou `migration` ;
5. confirmation qu'aucun secret n'apparaît dans les sorties ;
6. mise à jour des fichiers d'état avec les preuves réelles.

## Limites

Cette story ne réalise pas encore :

- corrélation distribuée complète entre requêtes et actions externes ;
- stockage centralisé/rotation avancée des logs ;
- observabilité métier exhaustive de chaque opération du vertical slice ;
- doctor/recovery complet.

Ces sujets restent dans le backlog correspondant, notamment US-0105 et les stories d'observabilité ultérieures.
