# S01 — US-0102 — Migrations sûres

## User story

En tant que développeur, je veux migrer une base sans destruction silencieuse.

## Critères d’acceptation du cahier des charges

- Les migrations sont versionnées, testées, traçables et refusent les opérations destructives non protégées.
- Le comportement est traçable et respecte les permissions/politiques de validation applicables.
- Les tests et la documentation nécessaires sont inclus avant Ship.

## Research

L’existant utilise déjà SQLx avec `sqlx::migrate!("./migrations")` dans `src/infrastructure.rs`. Les cinq migrations sont versionnées par leur nom et SQLx conserve leur historique dans `_sqlx_migrations`.

Constat sur l’existant au moment de la reprise :

- `0001_foundation.sql` contient le socle initial et les données de référence initiales.
- `0002_onboarding_operations.sql` et `0003_operating_model.sql` utilisent déjà plusieurs opérations additives idempotentes.
- `0004_storage_locations.sql` ajoute le stockage documentaire sans modifier la migration initiale.
- `0005_intelligence.sql` utilise `IF NOT EXISTS` pour ses tables et index.
- Aucune des cinq migrations actuelles ne contient `DROP TABLE` ou `TRUNCATE TABLE`.
- Aucune exécution SQL de migration ne doit être ajoutée au bootstrap US-0101.

## Design

Le mécanisme retenu est volontairement simple et natif :

1. `scripts/verify-migrations.ps1` constitue le gate statique.
2. `scripts/migrate.ps1` démarre PostgreSQL, vérifie le gate, prend un backup puis lance le migrateur Rust.
3. `src/bin/sci-family-migrate.rs` exécute le même `sqlx::migrate!` que l’application, sans second moteur de migration.
4. Un rapport horodaté est écrit dans `snapshots/`.

### Politique destructive

Par défaut, sont refusés :

- `DROP TABLE`
- `DROP COLUMN`
- `DROP SCHEMA`
- `DROP INDEX`
- `TRUNCATE`
- `DELETE FROM`

Une exception doit être explicitement matérialisée dans le fichier de migration par :

```sql
-- SCI-DESTRUCTIVE: APPROVED
```

Cette exception ne supprime pas l’obligation de review humaine ni de backup.
